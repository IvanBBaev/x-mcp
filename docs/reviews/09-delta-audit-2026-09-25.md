## 4. Findings

### Finding 1 — MEDIUM: `x_thread_create` charges the full thread cost before validating any post, and the error message misrepresents the charge

**Where**: `src/tools/posts.ts:622-631` (validation loop), `src/tools/posts.ts:605-613`
(`cost` resolver), `src/core/registry.ts` (pipeline step 4 budget check precedes step
5 handler invocation), `src/mcp/gates.ts:48-66` (`createBudgetGate` — charge happens at
`check`, before the handler runs; `reserve`'s settlement is skipped whenever
`units === undefined`).

**Mechanism**: `x_thread_create`'s `cost` resolver computes the *aggregate* price of
every post in the array up front (`$0.015` base / `$0.20` if the post text contains a
URL, per COST-4) and returns it as an absolute `usd` override. The registry's pipeline
charges that full amount at step 4 (`deps.budget.check(estimate)` → `budget.reserve`,
via `createBudgetGate`), strictly *before* invoking the handler at step 5. Only then
does the handler's own per-post whitespace-validation loop run
(`src/tools/posts.ts:623-631`):

```ts
// POST-1 applies per post; validate ALL of them before any HTTP call is sent.
for (const [index, text] of input.posts.entries()) {
  if (text.trim() === '') {
    throw validationError(
      `Post ${index + 1} of ${input.posts.length} is whitespace-only. Provide ` +
        'non-whitespace text for every post (POST-1); nothing was sent.',
    );
  }
}
```

If any post is whitespace-only, this throws a `validationError` that propagates
straight out of `registry.call()` — there is no try/catch across pipeline steps 3-7,
so step 6 (`budget.reserve(estimate, output.units)`, the settle/refund step) never
runs. The charge made at step 4 is final. `x_thread_create` also never sets
`output.units` on either return path (success or mid-thread `ok:false`), but that
turns out not to matter for a *refund* here regardless: `units`-based settlement only
rescales a `class`-priced multiplier, and this tool prices via an absolute `usd`
override, which `core/tooldef.ts`'s own documentation says is "never multiplied" by
units — so even a hypothetical `units` value could not have triggered a refund for
this failure mode. There is no refund path at all for a pre-HTTP validation failure.

**Empirically confirmed** with a throwaway local script (not committed) that drives
the real `registry`/`budget`/`gates`/`x_thread_create` code with a stub HTTP client
that throws if ever called: a 25-post thread — 24 posts each containing a URL
(`$0.20` each) plus one whitespace-only post at the end (`$0.015`, no URL match) —
produced:

- HTTP calls made: **0**
- Session spend before: **0**
- Session spend after: **4.815**
- Delta charged for a call that sent zero posts: **4.815** (= 24 × $0.20 + 1 × $0.015,
  matching `BASE_POST_USD`/`URL_POST_USD` in `src/tools/posts.ts:114,116`)
- Thrown error message: *"Post 25 of 25 is whitespace-only. Provide non-whitespace
  text for every post (POST-1); nothing was sent."*

**Why this is a defect, not just accepted risk**: `THREAD_COST_NOTE`
(`src/tools/posts.ts:582-584`) explicitly discloses that a thread which *stops early
after sending some posts* is "charged upfront and not refunded" — that is a
deliberate, disclosed design choice, and this audit does not challenge it. But the
validation-failure case is different in kind: **zero** HTTP calls are made, and the
error message itself says "nothing was sent," which is true only for the network
request and actively misleading about the budget — an agent reading that message has
no signal that ~$4.80+ was just charged for a call that sent nothing at all. The
blast radius scales with the new tool: the identical `text.trim() === ''` pattern
already exists in `x_post_create` (`src/tools/posts.ts:356-364`), but there it is
capped at a single post ($0.015-$0.20); `x_thread_create` amplifies the same pattern
to a full 25-post aggregate (up to ~$5.00). This is also the third instance in this
delta of the same underlying bug class — "a local, pre-network rejection still gets
billed" — being actively closed elsewhere: (1) `f2a0a76` reordered rate-limit
preflight ahead of the budget check so a RATE-2 refusal is no longer charged, (2)
`cf4ba3b` (COST-3) fixed reads being billed for more units than were actually
returned. This finding is the one place in the delta where the same class of bug was
introduced rather than fixed.

**Recommended fix**: move the whitespace check into the tool's own zod schema (e.g. a
`.superRefine()` over the `posts` array, mirroring the per-element-validation style
already used elsewhere in the codebase for array/string fields), so the rejection
happens at registry pipeline step 1 (zod validation) — strictly before step 4's budget
check — rather than inside the handler. This is deliberately narrower than changing
`x_post_create`'s established handler-level pattern (which the team may reasonably
leave as-is given its much smaller stakes): it targets only the one tool whose
charge-before-validate window has real financial weight, without restructuring the
registry's charge-then-settle contract or the handler-colocated-validation convention
the rest of `posts.ts` follows. At minimum, until fixed, the thrown message should
say plainly that the full thread cost was still charged, so the agent (and the human
behind it) is not misled by "nothing was sent."

### Observation O1 — LOW: F16's softer asks left open by design

`docs/reviews/03-security-review.md:210-213` (F16) asked that `x_thread_create`
"require `publish`+ and re-affirm the human-in-loop expectation; consider a lower
default cap and per-post visibility." Publish+ gating and per-post visibility are both
implemented; the cap remains at 25 (F16 only said "consider") and there is no new
explicit human-in-loop language beyond the tool sitting at `write:content`. Consistent
with 08's O1 treatment of a similarly-accepted design tradeoff — noted for the record,
not a finding requiring remediation.

## 5. Conclusion

The delta's non-tool substance is a clean set of hardening fixes: COST-3 closes a
real under-billing gap on every paginated/batch read tool, `f2a0a76` closes a
local-refusal-still-charged gap in the registry pipeline, T-320 F6 closes the
preemptive-refusal-training residual accepted in the 07 audit, and AUTH-11/12/14/16
each close a real, previously-identified gap (unknown token lifetime, duplicate
permission warnings, proxy-routed credentials, no browser ever actually opening on
`authorize`). Against that backdrop, `x_thread_create` — the delta's only new
tool — introduces one MEDIUM defect: it is charged in full before its own validation
runs, so a purely local, zero-HTTP rejection still burns the entire aggregate charge,
and the resulting error message ("nothing was sent") actively misrepresents that fact
to the agent. Policy gating, rate-limit bucket sharing, egress allowlisting, and
per-post result visibility for the new tool are all otherwise correctly wired and
consistent with the F16 design-time review. Scenario suite re-run 2026-09-25:
**14/14 pass, 0 fail, 0 cancelled, 0 skipped, 0 todo**. Remediation recommended for
Finding 1 before the next release; O1 is accepted as-is, no action required.
