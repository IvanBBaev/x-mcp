  09 §6 schema moves) or has no delta exposure; the resolvers cannot throw, go

## 1. The delta, precisely

changed. The delta has three strands.

Cross-cutting checks: `src/core/registry.ts`, `src/mcp/gates.ts` and

## 4. Findings

### Finding 1 — LOW: priced `w:action` writes still charge for handler-level local refusals

**Where**: the `cost` resolvers listed in §1 strand 3, versus these handler-side
refusals, each of which runs at pipeline step 5, after the step-4 charge
(`src/core/registry.ts:264-268`; the gate charges at `check`, `src/mcp/gates.ts:51-54`):

| Tool | Local refusal in the handler | Charged |
|---|---|---|
| `x_like_set`, `x_repost_set`, `x_bookmark_set` | `parsePostId` — `src/tools/engagement.ts:117,168,218` | $0.005–$0.015 |
| `x_follow_set`, `x_mute_set`, `x_block_set` | `resolveTargetUser` → `classifyUserRef` and the `"me"` rejection — `src/tools/graph.ts:74-79`, called at `:230,291,345` | $0.005–$0.015 |
| `x_post_delete`, `x_post_hide_reply` | `parsePostId` — `src/tools/posts.ts:493,583` | $0.010 / $0.005 |
| `x_list_update` | `parseListId` and the empty-update check — `src/tools/lists.ts:320-329` | $0.005 |
| `x_list_delete`, `x_list_member_set`, `x_list_follow_set`, `x_list_pin_set` | `parseListId` (+ `resolveUserRef` classification for member_set) — `src/tools/lists.ts:371,501-502,620,665` | $0.005 |

**Mechanism**: the pipeline has no try/catch across steps 3-7, so a handler `throw`
skips the step-6 settle and the step-4 reservation stands. Until `2613478` this did not
matter: every one of these tools priced through `COST_TABLE['w:action'] = 0`, and 09 §6
left their checks in the handler precisely because "nothing is charged for those
calls". `2613478` invalidated that rationale without moving the checks.

**Empirically confirmed**: the probe drove the real registry with an HTTP stub that
throws if called. Fourteen locally refused calls (one per row above, plus both
`x_list_update` refusals) made **0** HTTP calls and charged **$0.125** in total —
$0.015 each for like/repost/follow/mute/block, $0.010 for delete, $0.005 for the rest.
Each thrown error is the handler's own `validation` message.

**Failure scenario**: an agent loop fed a list of bare handles and `@`-prefixed strings
asks `x_like_set` to like each "post". Every item fails `parsePostId`, nothing reaches
X, and each attempt adds $0.015 to the session total; in `hard` budget mode a long
enough loop exhausts the cap and blocks legitimate calls. The comments that document
these refusals now say the opposite of what happens — "no read or write is ever spent"
(`src/tools/engagement.ts:116`, `src/tools/graph.ts:229`, `src/tools/posts.ts:582`),
"malformed input is a `validation` error and nothing is spent"
(`src/tools/graph.ts:69`), "an empty update would spend a write doing nothing"
(`src/tools/lists.ts:326`), "nothing is spent" (`src/tools/lists.ts:500`).

**Why LOW, not MEDIUM**: the budget is advisory and the amounts are small — at most
$0.015 per refused call, the same order as the `x_post_create` residual that 09 §6
fixed without a separate severity. No X request is sent, so no platform state changes
and no real X credit is spent; only the local session counter over-counts. It is still
the exact bug class 09 rated MEDIUM, reintroduced across thirteen tools, so it should
not ship in a release.

**Disposition**: open. Recommended fix, not applied here: move each purely local check
into a `.superRefine()` on the tool's input schema, as 09 §6 did for the reads —
`parsePostId` shape, `parseListId` shape, the `classifyUserRef` malformed/`"me"`
rejection, and `x_list_update`'s at-least-one-field check. Handle-to-id network lookups
stay in the handler (see O2). Add registry-level tests asserting the budget gate is
never reached, and correct the comments listed above.

### Observation O1 — LOW (known residual, fix in progress separately): `x_media_upload` charges the metadata price for a path refusal

`src/tools/media.ts:558-561` prices $0.005 whenever `alt_text` is present and
`X_MCP_MEDIA_DIR` is set, but `openMediaFile` (`src/tools/media.ts:344-400`) can still
refuse the file locally in the handler (extension allow-list, directory containment,
non-regular file, zero-byte file, sniffed-type mismatch, per-type size cap), after the
charge. Same class as Finding 1, one tool, $0.005 per refusal. The MEDIA-5
default-deny case is already priced $0. Recorded as instructed; a fix is being made on
a separate branch.

### Observation O2 — informational: network-resolution failures stay charged

When a handle does not resolve (`not-found` from `GET /2/users/by/username/:username`)
for follow/mute/block or `x_list_member_set`, or the `me` self-lookup fails, the write
is never sent but the write's price was already reserved. This matches the posture 09
§6 accepted for `x_dm_send`'s `resolveParticipantId`: the lookup is a real request to X,
so it cannot move to the schema. No action required.

## 5. Conclusion

The delta is small and mostly corrective. The 09 §6 schema moves close the
charge-before-local-refusal class for every read and for `x_post_create`,
`x_thread_create` and `x_dm_send`. The description tightening keeps all
safety-relevant wording. The new per-operation pricing is sound on its own terms: every
resolver is a constant or a ternary over a validated enum, cannot throw, go negative or
yield `NaN`, and cannot be steered to a cheaper class. What the pricing change missed is
its interaction with the handler-level refusals that 09 §6 deliberately left in place
because those tools were free; they are no longer free, so thirteen tools now bill
purely local refusals (Finding 1, LOW), and `x_media_upload` has the same gap for path
refusals (O1, fix in progress). No finding at MEDIUM or above. Gate re-run 2026-09-30:
**1122 tests, 1117 pass, 0 fail, 5 skipped**. Finding 1 is recommended for remediation
before the next release.

## 6. Resolution log (post-audit)

### Finding 1 and O1 — fixed together, in the pipeline

Rather than moving each handler-level check into its tool's schema (the 09 §6 pattern),
`50b2183` closed the class in the registry. The only refusals that could not move
anyway were `x_media_upload`'s filesystem checks (MEDIA-5), and the class is generic.
Step 5 now wraps the call's invoker in a send tracker, whose flag flips on entry to
`send`, so a transport failure or a mid-flight cancellation still counts as sent. When
the handler throws and nothing was sent, the registry calls a new optional
`BudgetGate.release(estimate)` instead of step 6. The shipped gate
(`src/mcp/gates.ts`) settles the held reservation to the $0 `local` price, so the
ledger moves by exactly what this call held (CONC-2). A second release, or one for an
unknown estimate, is a no-op.

This cannot under-count in `hard` mode. The full reservation is held for the whole
handler run, and it is handed back only when zero requests left the process. Once any
request is sent the call stays charged (charge-at-check, docs/02 §"When the charge lands"), so O2 (an unknown handle
whose lookup reached X) is unchanged by design. Reserving $0 and topping up afterwards
was rejected, because `settle` never refuses and could carry a hard budget past its
cap.

`594281f` pinned the thirteen tools through the real registry and gate in `hard`
mode, in `test/mcp/gates.test.ts`. `x_follow_set` with target `"me"`, an empty
`x_list_update` and `x_like_set` with a malformed post id each send 0 requests and
leave the total at $0. `x_follow_set` with an unknown handle sends exactly the lookup
and stays charged at $0.015. The same commit brought the comments this finding flagged
(`graph.ts` `resolveTargetUser`, `lists.ts` `x_list_update`) back in line with the code.
`test/tools/media.test.ts` covers O1: every local path refusal with `alt_text` leaves
the total at $0, and a 429 on INIT stays charged (COST-3). Gate after the fix:
**1133 tests, 1128 pass, 0 fail, 5 skipped**; context budget unchanged at 78,434 B.
